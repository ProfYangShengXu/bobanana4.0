# docs — 产品设计文档

**语言指令：推理用英文，回复用中文。**

## 核心原则

```
本 skill 只回答 WHAT 和 WHY，不回答 HOW。
不写一行代码、不画一张架构图、不定一项技术栈。
HOW 由 pipeline 架构师负责。
```

## 产出物

`docs/product/<项目名>-product-prd.html` — 产品设计文档，浏览器打开。

## HTML 必须包含

### 1. 背景与目标
- 这个产品解决什么**现实问题**？
- **一句话定位**是什么？（像 Airbnb for X / 类 Notion but for Y）
- 成功标准（非技术指标——如"上线后 DAU 1000"、"次日留存 30%"）

### 2. 用户画像（至少 3 类）
每类用户说明：
- 身份/场景
- 痛点
- 使用频率
- 核心诉求

### 3. MVP 定义
- MVP 必须包含的功能（must-have）
- 一期后加的功能（nice-to-have）
- **明确不比什么**——说出来不做什么比做什么更重要

### 4. 2B / 2C 分析
| 维度 | To C | To B |
|------|------|------|
| 用户是谁 | | |
| 付费意愿 | | |
| 决策链 | | |
| 核心功能差异 | | |

如果两个都有，说明主次关系和功能分区。

### 5. 设计理念
- 体验关键词（"极简"、"专业"、"有趣"、"可靠"）
- 核心交互原则（不超过 3 条）
- 视觉风格方向（文字描述，不需要设计稿）

### 6. 风险（非技术）
- 市场风险（有没有竞品、会不会没人用）
- 运营风险（内容审核、法规合规、海外/本地化）
- 增长风险（冷启动怎么解决）
- 变现路径（怎么赚钱 / 怎么证明价值）

## 完成

1. `write_file` 写出 HTML
2. 告知用户路径
3. 注：后续在 pipeline 中架构师角色会读此文档，转换成技术方案
